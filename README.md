# بوابة السلال الغذائية — ناتكو الاستهلاكية

تطبيق عربي لإدارة طلبات الموظفين وكتالوج المنتجات، مع صور المنتجات محفوظة داخل Cloud Firestore لتجنب الحاجة إلى خدمة تخزين ملفات مدفوعة.

## متطلبات إعداد Firebase

يلزم إنشاء مشروع Firebase تابع للشركة قبل أن يتمكن أي مستخدم من الدخول:

1. أنشئ مشروعاً في Firebase Console وأضف تطبيق Web. سجّل إعدادات التطبيق في ملف محلي غير مضاف إلى Git:

   ```powershell
   Copy-Item .env.example .env.local
   ```

   املأ قيم `VITE_FIREBASE_API_KEY` و`VITE_FIREBASE_AUTH_DOMAIN` و`VITE_FIREBASE_PROJECT_ID` و`VITE_FIREBASE_APP_ID` من إعدادات تطبيق Firebase.

2. فعّل **Authentication → Email/Password** وأضف نطاق الموقع إلى Authorized domains. لا يلزم تفعيل Phone للموظفين في مسار كلمة المرور.
3. أنشئ قاعدة بيانات **Cloud Firestore**. لا يحتاج التطبيق إلى تفعيل تخزين الملفات.
4. من مجلد المشروع، سجّل الدخول إلى Firebase CLI واختر مشروع الشركة، ثم انشر قواعد الحماية:

   ```powershell
   npx firebase-tools login
   npx firebase-tools use --add
   npx firebase-tools deploy --only firestore:rules,firestore:indexes
   ```

   راجع `firestore.rules` في مراجعة أمنية قبل الإطلاق. استخدام الخطة المجانية لا يضمن سعة غير محدودة: عند بلوغ الحصة المجانية قد تتوقف بعض العمليات حتى تجدد الحصة، دون ترقية المشروع إلى خطة تتطلب الدفع.

## إنشاء أول مشرف

لا يوجد مشرف افتراضي أو كلمة مرور ثابتة في الشيفرة:

1. أنشئ حساب المشرف يدوياً من **Firebase Console → Authentication → Add user**، ثم تحقّق من بريده.
2. انسخ UID للحساب، وأنشئ في Firestore مستنداً ضمن المجموعة `admin_users`، مستخدماً UID كمعرّف للمستند، وأضف الحقل:

   ```json
   { "active": true }
   ```

3. سجّل دخول المشرف من خيار البريد وكلمة المرور. وجود حساب Firebase وحده لا يمنح صلاحية الإدارة؛ الحساب الذي يحمل دور المشرف ينتقل تلقائياً إلى لوحة الإدارة بعد التحقق.
4. يمكن لمسؤول الموارد البشرية إنشاء حساب الموظف بعد اعتماد سجل نشط برقم هاتف فريد بصيغة دولية (`+967...`): افتح **الموظفون → تعديل الموظف**، وأدخل كلمة مرور أولية وأكدها ثم اضغط **إنشاء حساب وتعيين كلمة المرور**. ينشئ هذا حساب Firebase Authentication ورابط الموظف في Firestore؛ حفظ سجل الموظف وحده لا ينشئ حساب دخول.
5. يمكن للموظف أيضاً اختيار **إنشاء حساب موظف جديد** من شاشة الدخول، وإدخال الاسم ورقم الهاتف وكلمة المرور، والرقم الوظيفي إن توفر. ينشأ حساب داخلي وطلب مراجعة، لكن لا يُسمح بالدخول قبل أن يطابق المشرف الطلب مع سجل موظف نشط ويعتمده من قائمة **الموظفون**. لا يرسل التطبيق SMS ولا يتحقق تلقائياً من حيازة الهاتف؛ لذلك يجب على المشرف مراجعة الاسم والهاتف والرقم الوظيفي والتحقق من هوية الموظف قبل الاعتماد. البريد الداخلي مشتق من الهاتف ولا يظهر في الواجهة، ولا تحفظ كلمة المرور في Firestore.
6. من **المنتجات والصور** اختر **تجهيز المنتجات الأساسية** لمرة واحدة، ثم **تعديل / صورة** لإضافة صور المنتجات.
7. لإضافة أعداد كبيرة من الموظفين، افتح **الموظفون → تنزيل قالب CSV**، واملأ عمودي `email` و`employeeCode` ببيانات الموارد البشرية، وأضف الهاتف بصيغة دولية. البريد مفتاح داخلي فقط. راجع المعاينة ثم اضغط **اعتماد**. يقبل الملف حتى ١٠٬٠٠٠ موظف (٢ ميغابايت)؛ لا تضع كلمات مرور أو بيانات دخول في الملف. يمكن إعادة استيراد البريد نفسه لتحديث سجله.
8. يمكن أيضاً اعتماد موظف منفرد من النموذج أسفل استيراد القائمة.
9. لإدارة الشركات والفروع، افتح **لوحة المشرف → الشركات والفروع**. أضف كل شركة في بطاقة مستقلة، ثم حدد المحافظات التي لديها فروع فيها. أضف المحافظات من قسم المحافظات المتاحة، واربط المحافظة بأكثر من شركة عند الحاجة. بعد الحفظ، تتغير قائمة الفروع بحسب الشركة المختارة؛ الطلبات القديمة تحتفظ ببياناتها التاريخية.

## تجهيز كلمة مرور الموظف أو تغييرها

لا يدعم Firebase موفر هاتف/كلمة مرور أصلياً؛ يستخدم التطبيق عنوان Email/Password داخلياً مشتقاً من الهاتف، بينما يكتب الموظف رقمه وكلمة مروره فقط. التسجيل الذاتي ينشئ طلب اعتماد معلقاً ولا يمنح وصولاً قبل مراجعة المشرف وربطه بسجل نشط. لا يتحقق هذا المسار من ملكية رقم الهاتف عبر SMS، لذلك لا تعتمد الطلب تلقائياً. لا تشارك كلمة المرور داخل CSV أو Firestore.

لتعيين كلمة المرور الأولية استخدم لوحة **الموظفون → تعديل الموظف**. لا تُحفظ كلمة المرور في Firestore أو تعرض مرة أخرى بعد الإنشاء. لتغيير كلمة مرور حساب موجود أو استعادته، استخدم أداة Admin SDK المحلية من جهاز مسؤول موثوق؛ لا تنشر Cloud Functions ولا تُرسل SMS. تحتاج الأداة اعتماداً إدارياً لـ Firebase Admin SDK. احفظ ملف الخدمة خارج المستودع ولا ترفعه إلى GitHub:

```powershell
npm.cmd install --prefix functions
$env:GOOGLE_APPLICATION_CREDENTIALS = "C:\secure\natco-admin-service-account.json"
$env:GOOGLE_CLOUD_PROJECT = "natco-edabc"
node .\functions\manage-employee-login.cjs
```

تطلب الأداة رقم الهاتف المعتمد وكلمة مرور مرتين دون عرضها على الشاشة. تنشئ الحساب أو تغيّر كلمة مروره ثم تربطه بسجل الموظف النشط. إذا لم تُعدّ بيانات اعتماد Admin SDK، أوقف التشغيل واطلب من مسؤول Firebase تجهيز بيئة إدارية موثوقة؛ لا تضع مفتاح الخدمة في الواجهة أو المستودع. إذا كان حساب Authentication موجوداً مسبقاً، استخدم **ربط حساب موجود** من محرر الموظف لإضافة ربط Firestore دون تغيير كلمة مروره.

لا يوجد رمز مجاني لإعادة تعيين كلمة مرور عبر الهاتف على خطة Spark؛ الموظف يتواصل مع المشرف ليغيّر كلمة المرور من الأداة المحلية. لا تسجل كلمات المرور في السجلات أو الرسائل العامة.

## حساب يجمع دور الموظف والمشرف

يسجّل المشرف أو المدير حسابه من **إنشاء حساب** بنفس طريقة الموظف، ثم يؤكد بريده. بعد ذلك يمنحه مسؤول النظام صلاحية المشرف بإضافة `admin_users/{UID}` مع `{ "active": true }`. إذا كان سيستخدم خدمة الطلبات أيضاً، فيجب اعتماده كذلك كبريد موظف ورقم وظيفي من لوحة المشرف (مستند `employee_roster`). عند الدخول بحساب يحمل الصلاحيتين يفتح التطبيق مساحة الموظف، ويظهر زر **لوحة المشرف** بعد تسجيل الدخول للتبديل إليها؛ ومن لوحة الإدارة يمكنه الرجوع إلى مساحة الموظف. إنشاء الحساب أو التسجيل وحدهما لا يمنحان صلاحية المشرف.

قواعد Firestore تمنع العميل من منح صلاحية المشرف لنفسه. أضف مستند المشرف من Firebase Console أو من بيئة إدارية موثوقة فقط، ولا تضع بيانات اعتماد Admin SDK أو مفاتيح service account في تطبيق الويب.

## إشعارات الطلبات وGoogle Sheets

يُسجل التطبيق كل طلب جديد وإشعاره في عملية Firestore واحدة. يعالج Google Apps Script طوابير الإشعارات وتغييرات الموظفين والكتالوج كل خمس دقائق بدفعات محدودة، ويرسل رسالة من حساب Google الذي فوّض السكريبت ويضيف الطلب إلى Google Sheets. لا تُرسل بيانات الطلب إلى خدمة خارجية إلا إلى عناوين البريد والجدول المحفوظين في **لوحة المشرف → الإشعارات**.

### إعداد Apps Script

1. انشر قواعد Firestore المحدثة من مجلد المشروع قبل استقبال الطلبات:

   ```powershell
   npx.cmd firebase-tools deploy --only firestore:rules
   ```

2. افتح [script.google.com](https://script.google.com) وأنشئ مشروعاً مستقلاً. انسخ محتوى `integrations/google-apps-script/Code.gs` إلى `Code.gs`.
3. من **Project Settings** فعّل عرض ملف البيان `appsscript.json`، ثم استبدل ملف البيان بمحتوى `integrations/google-apps-script/appsscript.json`. يستخدم السكريبت `MailApp`، لذلك يجب أن يتضمن البيان نطاق البريد `https://www.googleapis.com/auth/script.send_mail` (وليس `gmail.send`).
4. في Google Cloud Console للمشروع المحدد في `FIREBASE_PROJECT_ID`، أضف **حساب Google مؤسسياً مخصصاً لهذا التكامل** إلى **IAM → Grant access** بدور **Cloud Datastore User** (`roles/datastore.user`). يمنح هذا الدور وصولاً مباشراً واسعاً إلى Firestore على مستوى المشروع؛ لا تمنحه لحسابك الشخصي أو لمستخدم لا تثق به. القيمة الافتراضية لمعرّف المشروع داخل السكريبت هي `natco-edabc`. إن كان مشروع Firebase مختلفاً، أضف Script Property باسم `FIREBASE_PROJECT_ID` وضع معرّف مشروعك.
5. من محرر Apps Script شغّل `initializeNatcoIntegration` مرة واحدة ووافق على صلاحيات Firestore وGoogle Sheets وMailApp والمشغلات. إذا أضفت نطاق البريد بعد التفويض الأول، احفظ البيان وشغّل الدالة مجدداً لقبول الصلاحية الجديدة. ينشئ السكريبت جدولاً جديداً عند الحاجة، ويضبط مشغلاً كل خمس دقائق يعالج دفعات صغيرة من التغييرات الجديدة فقط. كما يستبدل مشغلات المزامنة القديمة كل دقيقة ومشغلات المسح الكامل المجدولة. التهيئة لا تعيد مزامنة كل التاريخ تلقائياً.
6. افتح **لوحة المشرف → الإشعارات**، حدّد حتى ٢٠ بريداً واحفظ الإعدادات. يظهر رابط الجدول الذي أنشأه السكريبت ويمكن تغييره من الشاشة نفسها. عند استخدام جدول آخر، امنح حساب Google المشغّل صلاحية محرر عليه.

البريد يُرسل من حساب Google الذي وافق على السكريبت، ويخضع لحصة الإرسال اليومية في MailApp. مزامنة الصف إلى Sheets مستقلة عن نجاح البريد حتى لا يمنع فشل الإرسال حفظ الطلب في الجدول. عند تغيير المشرف لحالة طلب أو تعليمه كمحذوف، يُحدّث Apps Script صف الطلب نفسه بدلاً من إضافة صف مكرر؛ ويُلوّن الصف بحسب الحالة، مع تمييز المحذوف بالأحمر. الحذف هنا **حذف منطقي** يحفظ سجل الطلب ويجعله غير ظاهر للموظف، ولا يمسح بياناته نهائياً.

لا يجدول المزامن فحصاً شاملاً للموظفين أو المنتجات أو الطلبات. يعالج في كل دورة عدداً محدوداً من عناصر طوابير التغييرات، وتكتشف مشغلات تعديل الجدول تغييرات الموظفين والكتالوج مباشرةً. إذا تجاوز Apps Script حصة `UrlFetch` اليومية، يوقف طلبات Firestore والمزامنة المجدولة لمدة ٢٤ ساعة، ويترك العناصر غير المكتملة في الطوابير كي تستأنف بعد انقضاء التوقف بدلاً من تكرار الاستثناء في كل تشغيل. لتطبيق الإصلاح على مشروع Apps Script الحالي:

1. حدّث محتوى `Code.gs` من الملف الموجود في المستودع.
2. شغّل `repairNatcoTriggersNow` أولاً. هذه الدالة لا تتصل بـ Firestore؛ تزيل المشغلات المتكررة ومشغلات المسح الكامل القديمة، وتنشئ مشغلاً واحداً آمناً كل خمس دقائق، وتوقف محاولات Firestore لمدة ٢٤ ساعة كي لا يستمر الإشعار بالفشل أثناء تجدد الحصة.
3. بعد انتهاء التوقف، شغّل `initializeNatcoIntegration` مرة واحدة لإكمال تهيئة الجدول ومشغل تعديلات الصفوف. ستبقى العناصر غير المكتملة محفوظة في الطوابير وتُستأنف تلقائياً.

لا تنشئ مشغلات زمنية مستقلة لـ `syncAllNatcoData` أو `syncAllNatcoEmployees` أو `syncAllNatcoProducts` أو `syncAllNatcoOrders` أو `syncDeletedNatcoOrdersNow`. المزامنة التاريخية الكاملة متاحة يدوياً من قائمة الجدول **إدارة ناتكو → مزامنة كاملة مع التطبيق**؛ شغّلها عند الحاجة فقط، ولا تجعلها مشغلاً دورياً. يمكن تشغيل `retryNatcoOrderQueueNow` للمحاولة ضمن حدود المعالجة المعتادة، من دون تجاوز التراجع التلقائي أو إعادة ضبط كل العناصر دفعة واحدة. بعد تعديل التكامل، انسخ `Code.gs` وملف البيان إلى Apps Script وانشر قواعد Firestore المحدّثة. يتطلب حساب السكريبت صلاحية IAM المذكورة، ولا تضع كلمات مرور أو مفاتيح Service Account في الموقع أو ملفاته.

يحدّث التكامل تبويب **سجل الموظفين** من طابور التطبيق كل خمس دقائق، بحد أقصى ثلاثة سجلات موظفين وثلاثة منتجات وثلاثة طلبات في الدورة، ويراقب تعديلات الصفوف في Google Sheets ويرجعها إلى Firestore مباشرةً؛ عمود بصمة المزامنة مخفي ويستخدم لاكتشاف الصفوف المتغيرة عند المزامنة اليدوية. عند بداية شهر UTC جديد، ينشئ نسخة ثابتة باسم **أرشيف الموظفين YYYY-MM** من كشف الشهر السابق، ثم يصفر إنفاق الشهر في التبويب الحالي ويحدّث سجل الموظف. يظل السقف الشهري كما هو. عند الاستيراد أو المزامنة اليدوية، الخانة الفارغة في عمود موجود تمسح قيمة الشركة أو بيانات الملف المقابلة، والخانة الفارغة للسقف تزيل السقف، والإنفاق الفارغ يعني صفراً؛ أما العمود غير الموجود في الملف فلا يغيّر قيمته الحالية.

## تسجيل الموظفين وتلقي الطلبات

- يعتمد المشرف قائمة بريد الموظفين وأكوادهم دفعة واحدة عبر CSV، أو يعتمد مستخدماً منفرداً من لوحة الإدارة. لا تُفتح صلاحية الدخول لمجرد معرفة نطاق البريد؛ يجب أن يكون البريد نفسه موجوداً في القائمة المعتمدة.
- ينشئ الموظف حساباً ببريده وكلمة مروره، ويؤكد البريد من رسالة Firebase، ثم يسجّل الدخول من نموذج الدخول المعتاد. لا يُسمح له بقراءة بيانات المنتجات أو إرسال الطلبات قبل اعتماد بريده وتطابق كوده الوظيفي.
- تُحفظ ملفات الموظفين والطلبات في Firestore، وتظهر الطلبات الجديدة مباشرةً في تبويب **الطلبات**. يمكن للمشرف تحديث الحالة إلى قيد التجهيز أو جاهز للصرف أو تم التسليم أو ملغي؛ وتُزامن تغييرات الحالة والحذف المنطقي مع صف الطلب نفسه في Google Sheets.
- يمكن للمشرف فتح محادثة واتساب يدوياً لإشعار الموظف. إشعارات البريد للطلبات الجديدة تُعالج عبر إعداد Apps Script أعلاه.
- تُحفظ صور المنتجات داخل مستند المنتج في Firestore، بصيغ JPG أو PNG أو WebP وبحجم ملف أقصى ٦٠٠ كيلوبايت. تُحفظ بايتات الصورة الأصلية دون ضغط أو تغيير أبعاد، لكن الصور الأكبر من الحد تُرفض بدلاً من تصغيرها. الحد ضروري لأن حجم مستند Firestore الأقصى ١ ميغابايت، كما أن ترميز الصورة يزيد حجم البيانات.
- الصور القديمة التي كانت روابطها في خدمة تخزين الملفات تحتاج إلى إعادة رفع من **المنتجات والصور → تعديل / صورة**؛ الخطة المجانية لا تتيح قراءة تلك الملفات.
- صور المنتج تزيد استهلاك سعة Firestore ونقل البيانات عند عرض الكتالوج. ضمن Spark توفر Firestore حصة مجانية محدودة (منها ١ غيغابايت تخزين و١٠ غيغابايت نقل بيانات شهرياً حسب وثائق Firebase الحالية)؛ تجاوز الحصة يوقف الخدمة على Spark ولا يرقّي المشروع تلقائياً إلى خطة مدفوعة. راقب الاستخدام من وحدة التحكم. إذا كان المطلوب صوراً غير محدودة أو أكبر حجماً، لا يمكن ضمان ذلك مجاناً بهذا التصميم.

## التشغيل والفحص

```powershell
npm install
npm run dev
npm run build
npm run lint
```

يقرأ التطبيق إعداد Firebase من `.env.local`. إذا لم تُضبط القيم، يُعطّل تسجيل الدخول ولا يعرض رمزاً تجريبياً أو يحفظ طلبات محلية توحي بأنها وصلت إلى الشركة.
